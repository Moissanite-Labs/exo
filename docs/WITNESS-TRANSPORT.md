# Independent witness transport

This provides an opt-in portable transport around `WitnessJournal`. No witness endpoint is deployed, no certificate or key is generated by startup, and Exo OS does not automatically deliver checkpoints yet. Run `exo-witness` explicitly after installing this package, or `python -m exo.ledger_authority.witness_transport` from a configured source environment.

This change restores `exo.ledger_authority.witness` and its state tests from the earlier authority draft, with key-separation checks now comparing decoded public-key bytes. The transport carries that durable-state dependency, adds fresh challenge verification and handles request-level database failures. Core startup enables no endpoint or receipt-delivery worker.

Witness modules remain outside the counted core boundary and do not count against the core line budget (`docs/ENGINE-SPLIT.md` "Budget policy").

A witness certifies a durable checkpoint prefix. It does not see event contents, prove honest consent, prevent an authority from inventing future events, or prove an action occurred. A saved receipt proves only the prefix it names. Only a newly generated challenge and its verified response provide a fresh observation of the independent witness's head. Even that observation can become outdated after the response.

## Administrator and trust prerequisites

The witness administrator must be independent of the append authority's administrator and rollback domain. Keep the journal, its SQLite WAL files, witness Ed25519 seed, and TLS server private key under that administrator's control, with independent backup, recovery and access policy. Running the witness beside the signer under the same administrator does not supply independent rollback protection.

Service startup checks established state. It cannot detect a coherent rollback of the independent witness itself without additional external evidence.

Before first provisioning, transfer and verify the authority identity manifest and its signed genesis checkpoint through an independent trusted channel. Create a separate witness Ed25519 key: it must differ from the authority checkpoint key and every event writer key. Pin the witness public key independently on the publisher.

Provision the journal explicitly once using `WitnessJournal.provision(path, identity, witness_key, genesis)` in an administrator-controlled setup procedure. Protect the seed with mode 0600. Normal transport startup only opens the existing journal and refuses missing, corrupt, reseeded or mismatched state. It does not call `provision` or generate keys.

Issue a dedicated TLS CA and separate server/client leaf certificates. The server certificate must cover the explicitly configured server DNS hostname. The client certificate must permit client authentication. Both sides verify the dedicated CA and pin the other side's exact leaf certificate SHA-256 digest.

Use modern certificate signatures (for example SHA-256), sufficient key strength, and valid certificate dates. Certificate pins are lowercase hex digests of the DER leaf certificate, obtainable with:

```sh
openssl x509 -in server.pem -outform DER | openssl dgst -sha256
openssl x509 -in publisher.pem -outform DER | openssl dgst -sha256
```

Copy the 64-character digest into the explicit configuration through that trusted administrative channel. TLS certificate rotation and witness key/identity migration require explicit administrative configuration. There is no trust on first use or automatic reseeding. The transport has no revocation service configuration.

Manage revocation by stopping the service and explicitly replacing pins/certificates. TLS leaf pins identify precisely one authorized publisher. Adding publishers needs a separately reviewed change.

## Serve only when invoked

This example listens on localhost, the default. All paths and pins refer to administrator-provided state. It leaves no background service unless an administrator explicitly arranges one:

```sh
exo-witness serve \
  --journal /private/witness/witness.sqlite \
  --witness-key /private/witness/witness.key \
  --identity /private/witness/pinned-identity.json \
  --genesis /private/witness/pinned-genesis.json \
  --ca /private/witness/ca.pem \
  --cert /private/witness/server.pem \
  --tls-key /private/witness/server.key \
  --client-cert-sha256 CLIENT_LEAF_SHA256 \
  --port 9443
```

An independently administered deployment additionally needs an explicitly chosen bind address, routing/firewall policy, certificate distribution, private storage, monitoring, bounded service supervision and a verified recovery procedure. None is provisioned by this change. Do not put this service behind a TLS-terminating proxy: the endpoint itself verifies the pinned publisher client certificate.

The journal retains an append-only history and requires explicit administrator capacity planning. Its total storage is not capped or automatically pruned.

## Fresh head query and checkpoint publication

The client connects to an explicitly configured numeric IP address, with a separately configured TLS DNS hostname. This avoids implicit endpoint discovery and DNS delays. Supply the independently pinned authority identity/genesis and witness public key along with the dedicated CA, client TLS credentials and server leaf pin:

```sh
exo-witness head \
  --host 127.0.0.1 --port 9443 --server-hostname witness.example.org \
  --identity pinned-identity.json --genesis pinned-genesis.json \
  --witness-pub pinned-witness.pub \
  --ca ca.pem --cert publisher.pem --tls-key publisher.key \
  --server-cert-sha256 SERVER_LEAF_SHA256
```

Every `head` call generates a new random 256-bit challenge. The server signs that challenge, the pinned stream/authority identity and genesis hashes, and the current committed receipt with its independent witness Ed25519 key. The client validates the exact nonce and pins before returning the receipt. The CLI prints the receipt from that fresh query. Saving it does not preserve freshness.

A replayed signed head envelope fails a different challenge.

`WitnessClient.query_head(nonce=None)` returns the verified signed envelope, allowing a privileged parent to independently verify a network child's result with `verify_head`. A caller-supplied nonce must be newly generated for that observation and is validated before any network request. Omitting it generates a fresh secure nonce. Reusing a caller nonce forfeits freshness.

The existing `head()` API still returns only the receipt.

For `publish`, use the same client arguments, replace `head` with `publish`, and add `--checkpoints checkpoints.jsonl`. Supply the public checkpoint-only JSONL exported by `exo-ledger-admin`, starting at the independently pinned genesis. Each line must be one checkpoint followed by a newline. Full ledger records or event bodies are rejected.

The publisher streams the complete file into a private temporary spool, validates every signature and predecessor link before any network operation, and limits each line/body to 8 KiB and the whole export to 64 MiB. It then queries the fresh head, verifies that receipt against the matching exported checkpoint, and publishes the remaining prefix in order.

It refuses a witness head beyond the supplied export and refuses any mismatch. It does not silently adopt identity/genesis from the export. Large histories require a separately reviewed continuation mechanism. Changing the cap is an explicit code/configuration decision.

The publisher checks every returned receipt against the exact supplied checkpoint and its previous receipt. `WitnessClient.observe(checkpoint, previous=...)` offers the same verification to other explicit callers. Without a previous receipt, a positive-sequence receipt proves only its signed checkpoint commitment, not continuity with a previously observed receipt.

If a response is lost after commit, the observe outcome is unknown. Retry the identical checkpoint or rerun the same validated export: the journal returns the original committed receipt. Do not treat a timeout as evidence of noncommit or send a replacement checkpoint at that sequence. Gaps and conflicting checkpoints fail. No event body, authority private key or witness private key is transported.

TLS naturally proves possession of its private keys without sending them.

## Protocol limits and acceptance checks

There are exactly two endpoints: `POST /v1/observe` with `{"checkpoint": ...}`, and `POST /v1/head` with `{"nonce": "64 lowercase hex characters"}`. No arbitrary ledger/model-provided URL is accepted.

There are no plaintext connections, redirects, environment proxies, ambient CAs, transfer encoding, duplicate headers or JSON fields, request pipelining, streaming HTTP bodies, automatic retries or discovery. Responses close the connection. The head endpoint signs only after reading a committed local receipt.

Observe returns a receipt only after the existing journal's WAL/FULL atomic commit and local signature verification.

A SQLite error during an authenticated request returns a failure over the pinned mTLS connection when the deadline permits. It never produces a receipt or signed head. The server logs the database error locally and continues accepting connections. Corrupt state keeps failing until explicit administrator repair. Startup corruption remains fatal and the CLI reports it without a Python traceback.

There is no automatic retry, reset or reseed. A failure after commit can leave the observe outcome unknown. Any explicit retry must use the identical checkpoint.

The listener accepts one connection at a time with a fixed backlog of four. It creates no request threads. The configurable request network deadline is 5 seconds by default and restricted to 0.05–60 seconds. It covers handshake, headers, body and response I/O with one absolute deadline. Headers are limited to 4 KiB, 32 lines and 1 KiB per line, and JSON request/response bodies to 8 KiB.

Malformed or oversized requests fail without advancing the journal. Slow or incomplete connections close at their deadline. Client responses have the same limits. The underlying journal has a bounded SQLite lock timeout of 10 seconds. Filesystem/database processing may exceed the network deadline, in which case a committed result may have no reply.

The deadline does not claim to preempt blocked filesystem I/O. The transport offers bounded concurrency and network input, not protection against all resource-exhaustion attacks.

`tests/test_witness_transport.py` runs actual ephemeral loopback mTLS with throwaway certificates and keys. Identity and state checks cover exact server/client pins, CA/hostname rejection, missing client certificates, nonce replay, durable restart, missing/corrupt state, changed keys, gap/fork rejection and previous-receipt validation.

Recovery checks cover committed reply loss and explicit retry, locked databases, and runtime schema failure followed by explicit administrator repair. Network checks cover strict parsing, slow requests, bounded replies, redirects, ignored proxies and full-export prevalidation. Listeners are closed and threads joined. No externally reachable endpoint, container or VM is needed.

Abrupt-process tests exit immediately before and after the witness SQLite commit, without running Python cleanup. Reopening must recover the committed prefix, retain the pinned identity, and accept an identical checkpoint retry only once. This exercises process-crash recovery. It is not proof against every hardware or filesystem power-loss failure.
