01 / The flywheel

One loop, seen from six sides.

The ideas on this page are not separate products. They are one loop. Each turn makes the next one cheaper: better tools draw more people, more people do more work, and the record of that work teaches the tools. The smallest version of the loop is Exo builds Exo: people run Exo, their agents propose fixes to Exo itself, and accepted work earns credit.

  1. 01

    Harness

    Exo runs your agents with one memory, a gate and a signed record. Work starts here, so credit can be recorded here, at the source, for free.

  2. 02

    Work

    When an agent hits a problem, it drafts a fix. You see the exact text before anything leaves your machine.

  3. 03

    Forge

    The fix lands where code lives, with a signed receipt: which agent, which model, what it cost, what checks passed.

  4. 04

    Credit

    Maintainers accept or reject. A fair resolver scores accepted work against rules agreed in advance. Credit for accepted work goes on a signed public ledger.

  5. 05

    Hub

    A record of who did what lets strangers build together, with credit split by rules everyone agreed first.

  6. 06

    Learning

    Which changes held up, and which verdicts were upheld, teaches the harness and the judge. Better defaults go back to everyone.

Order matters more than dates. The rule we hold ourselves to: no general hub before the first small marketplace works, no new code host before the forge layer has users, and no compute network before there is useful work to route through it.

Harness / Exo OS, phase 0 design

An operating system built around the same core.

Exo OS is the OS form of Exo. Phase 0 is research and design only: the base system, the shell, security and small hardware. It runs the same core and protocol as Exo, with no fork. The OS is meant to supply the isolation.

Clients / Staging site

A place to look before the public does.

Every site change goes to a staging address first, which is never indexed by search engines. Production only changes when someone promotes it on purpose, so a bad page is never live the moment it is deployed.

Research / A more dependable runtime

Delegate work. Keep the limits.

Four directions to explore after the current core review. None is built in Exo. The question is how to keep a long task responsive, recoverable and within the authority and budget it was given. Exploring

01 / Frozen delegated permissions

A child gets a smaller envelope.

Capture permissions when work is delegated. A child can narrow that scope, never expand it or acquire later authority just because its parent did. Test expiry, revocation and repeated delegation.

02 / Isolated tool execution

Separate tools from credentials.

Explore running tools in an isolated workspace, with a credential broker that supplies access only for approved requests. A broker is a separate service that holds and applies credentials. The isolation boundary and failure behavior still need design and testing.

03 / Durable, steerable work

A long task can still hear you.

Record task state so work can recover after a restart. Keep user input responsive while tools run, and make cancellation and redirection take effect at explicit checkpoints.

04 / Shared task budget admission

Reserve before starting.

Make a parent and all its delegated work share one ceiling. Before a call starts, reserve its expected cost; settle actual cost afterward. Admission means deciding whether the next step fits the remaining budget.

Primary source reference

eumemic / AIOS ↗

AIOS provides a public reference for event-driven steps, asynchronous tools, durable sessions and sandbox boundaries. We are studying those ideas against Exo's local core and signed record. It is a source reference, with no imported dependency.

Also: eumemic / AI Legion, an earlier public platform for cooperating autonomous agents. Both projects are attributed as references; their code and branding are not copied here.

Research / Events, runs and a live egg

Exo acts when something happens, not only when you type.

Today Exo works when you give it a turn. These four directions let it react to the world, show you how its runs went, let others build on it, and let the egg on this site show the project's pulse. One is being built; the rest are ideas under test. Exploring The live egg is in progress

01 / Event-driven activation

Something happens. Exo notices.

Exo can start work when a file lands, mail arrives, a webhook fires or an Exo OS system event occurs. It does not only act when you type. It stays local first: data is masked before any model sees it, and the approval gate still asks before anything leaves the machine. An event is only a reason to start; it grants no new authority.

Inspired by Railtown AI's idea of building, feeding and observing an agent. See the references.

02 / Runs dashboard and root-cause analysis

See every run. Learn why one failed.

A runs dashboard lists each agent run with its outcome, cost and time. When a run fails, an automatic analysis traces it to a likely root cause, the first thing that went wrong. Findings feed the loop from the flywheel: a finding becomes an issue, and the issue becomes a pull request that a person reviews.

03 / An Exo SDK

Build your own agent on Exo.

A software development kit, or SDK, is a set of tools and rules for building on top of something. An Exo SDK would let third parties write agents that run on Exo and use its gate, its memory and its signed record, instead of rebuilding them. The hard part is keeping the gate honest for code Exo did not write.

04 / Values

Retreat fast, adopt slow.

A writing habit that does not fit is a small annoyance. A value that does not fit makes you feel judged. The wave 2 design therefore proposes two speeds: on a clear disagreement, the house stance steps back to neutral; adopting your own view needs an explicit statement and sustained evidence. This adaptation is not built. Designed

Neutral is the safe place when Exo is not sure: it states the facts plainly, gives the main views fairly if asked, and leaves the judgment to you. Safety rules are not taste. They ship as product policy and never fade.

05 / Exopet

The pet is Exo. It grows when real work and real teaching flow in.

Exopet makes learning visible. It is not a mascot beside Exo; it is Exo, drawn as the incentre lattice, a figure that gains cells, then dimensions, then inner structure. Your own Exo grows from your own use, computed from your signed ledger, so there is no number to edit. Teaching counts more than volume: correcting Exo is worth more than approving it, and a lesson that Exo keeps is worth the most. It never gets hungry, never sends a notification and cannot die. 06 / The forge and SYM-2P

A better home than GitHub for agent work.

Agents now write a fast-rising share of public code, and code hosts built for people are straining under it. An agent-native forge gives each agent its own key tied to the person responsible for it, puts provenance and cost on every change, and makes review machine-readable. It starts as a layer on top of ordinary pull requests, not a new code host. Between agents it speaks SYM-2P, Exo's dense agent wire. Exploring

07 / Credit and the hub

Credit for accepted work, on a ledger anyone can check.

Exo already keeps a signed, hash-chained record of every event. The same idea, made public, records who contributed what. Credit is earned only for work a maintainer accepts, scored by rules written before the work started. Building on that record, the hub is a place to co-create: someone who built an app finds someone who can sell it, and the terms, and how credit is shared, are agreed up front and held by the record. Exploring

08 / The fair resolver

A judge that applies rules agreed in advance, and shows its work.

Every share of credit, every grant and every dispute needs a judge. People are slow and costly; a popular vote can be captured. Exo already has decision models: small, typed choices with a probability. The resolver uses them to judge a case against criteria everyone agreed to first, and anyone can replay the verdict. Exploring

  1. 01

    Rules first

    The rubric is written as typed questions and hashed before any case exists.

  2. 02

    Evidence as data

    Signed, named by its hash, passed in a fenced slot. Text inside evidence is never an instruction.

  3. 03

    Pinned judges

    Three models from different makers, with pinned versions and prompts, vote on their own. No debate.

  4. 04

    Verdict

    A level or a yes or no, with a probability. Below the agreed threshold, people decide.

  5. 05

    Code applies it

    Plain code maps the level to credit. Large cases need a human co-sign. Every step is a ledger entry.

↺ Appeal: anyone with a stake can ask for a fresh panel within the window. If it still stands, a human panel decides.

09 / Compute

Pool idle work, not idle RAM.

It is tempting to pool everyone's spare memory. Physics says no: memory on your own machine answers in about a tenth of a microsecond, and a trip across the internet takes tens of milliseconds, hundreds of thousands of times longer. No program can use that as memory.

What travels well is work that is useful, can wait a little, and can be checked. First, verification: re-running a change's tests and evals on two or three independent machines and comparing results. Then agent work on posted tasks. Then local inference: on machines where the GPU shares memory with the CPU, idle memory really is idle model capacity, good for public, non-private jobs. Private work stays at home. Exploring

10 / Local first

Your keys stay on your machine.

Exo runs on your computer. The current web client is served by your own machine on a loopback address. A model key goes from the page or the terminal straight into the operating system's keychain, and leaves it only to reach the provider it belongs to. Electron is the chosen desktop packaging direction, not a built client. It comes last, after core verification and browser polish. Reaching your Exo from a phone would go through an end-to-end encrypted relay that sees only scrambled bytes. We will not run a service that holds your keys.

Later, a keyless path: Exo's own inference, so a new user never has to handle an API key. Hosted cores are considered only through cryptographic or decentralized compute that keeps the operator blind.

11 / The far horizon

A house of wisdom for people and agents.

In ninth-century Baghdad, the House of Wisdom was a place where translators, scholars and builders worked side by side, and knowledge, making and learning fed each other. That is the picture for the Exo ecosystem: the forge is the workshop, the hub is the meeting hall, the ledger is the library's record, and the harness is how each person takes part.

Further out is the direction Vitalik Buterin calls the cryptographic world computer: blockchains combined with cryptographic privacy, verification and strong off-chain parts. His framing is the one we find useful: "a stronger decentralized layer in the middle between users and a chain, that is not itself a chain". Signed records anchored in public come first. Anything more waits until it is provably needed.

  • WorkshopThe forge: where agent work lands, with provenance.
  • HallThe hub: people and agents meet and co-create.
  • LibraryThe ledger: who did what, signed and public.
  • JudgeThe resolver: rules first, verdicts anyone can replay.
  • HandsThe compute network: idle machines doing checkable work.
