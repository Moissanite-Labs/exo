01 / The problem

Models get smarter every month. Working with them still feels like meeting a stranger every morning.

They forget

A new session starts from zero. Your context lives in one vendor's chat history, or nowhere at all.

They do not learn

You correct the same mistake again and again. The fix lives in one session and dies with it.

They eat your attention

Approve this, confirm that. People cannot watch quiet systems all day, so endless approval queues fail.

Everything is split

Agents, memory, sessions, dashboards and notes are separate tools. None of them shares what it knows.

What stops people from handing real work to models is missing context, not missing intelligence. Exo exists to close that gap.

02 / Vision

One system. Five jobs that are usually separate.

The idea comes from Gwern's essay on guardian angels: a model of you that works on your behalf, knows how you think, and asks when it is unsure. Exo builds that idea into a working harness.

  1. 01

    Guardian angel

    A model of you, built from a signed record of your work and words. It knows how you think, decide and write, and asks when it is unsure.

  2. 02

    Harness

    Agents that do the work: an orchestrator, role agents, tools, and routing across cloud and local models.

  3. 03

    Memory

    A continuing relationship across sessions, platforms and agents. Every belief can answer: why do you believe this?

  4. 04

    Context and sessions

    Budgeted retrieval, summaries that keep what matters, branching and clean handoffs.

  5. 05

    Command centre

    One view of every project, every running agent and task, and every decision waiting on you.

Goal one

Fit one person deeply

A guardian angel is only worth having if it really knows you. Exo learns your rulings, your voice, your taste and your limits, and keeps learning.

+

Goal two

Work for anyone

The core is generic. Everything about a person lives in their own store, built by an onboarding interview. A fresh install with an empty store runs end to end.

Every part of Exo splits the mechanism, which ships to everyone, from the person, which lives only in their own store. Nothing in the core may assume one user's accounts, machines or names.

03 / Horizon

Later, a companion you can carry.

In a few years, Exo should live in a small portable device, something like a mini robot or a charm you wear, that grows and evolves with its user. We design for that now: the personal store is one portable folder, the core stays lean on purpose, and there is a small, local model path from day one.

  • StoreOne folder. Moves to a new machine or a device.
  • CoreLine budget, checked by tests from wave 1.
  • ModelsLocal small-model defaults. Cloud when worth it.
  • ProtocolWorks over a slow link, a tiny screen, or voice only.

01

The signed ledger

Every event is written once to an append-only log: what you said, what you ruled, what agents did, and whether you accepted, edited or rejected it. Each entry is signed with Ed25519 by its author and chained by hash to the one before. The ledger is the source of truth. Your profile, memory, skills and indexes are views built from it. When a better model arrives, it catches up by replaying the log.

02

The principal store

Everything about one person lives in one portable folder: a one-page pack, a router, typed belief nodes with evidence and confidence, imported items like bookmarks and notes, and the ledger. Agent and group stores nest inside it. Search runs on your machine: keyword search and embeddings from a small local model, merged, then expanded along links, under a token budget. Your text does not leave the machine to be embedded.

03

Memory in tiers

Each tier is rebuilt from the one below it. Taste, stance and rulings live in the pack, loaded every turn. Facts, dates and people live in beliefs, fetched with sources when needed.

T0LedgerEvery event, signed. Never loaded into a prompt.
T1BeliefsClaims with evidence, confidence and validity dates. Retrieved under a budget.
T2PackOne page: identity, rulings, voice, gates. Loaded every turn, cached.
T3Working contextThe prompt for this turn. Built fresh.

04

Fresh context every turn

Exo does not drag a growing transcript behind it. Each turn is a fresh model call, built from a summary tree of everything so far plus the recent messages word for word. The turn waits until the summaries catch up, so nothing slips through. Summaries run in parallel, with separate queues for live chat and imported history. Long sessions stay sharp instead of slowly getting worse.

05

Gates by reversibility and exposure

Not every action needs your eyes. Reversible, private actions run fast and get logged. Irreversible, public, financial or third-party actions wait for your answer, with a link and a sensible default. Every external act is tied to a named person. Safety rules that protect other people sit outside the model of you.

06

Decision models for small choices

Picking a tool, a panel, a model or a label does not need a frontier model. Exo sends these to a decision role: small models that return probabilities, not prose. The default is Laya, running locally, free and private. Users can choose TypeSafe Jev, Perplexity's decider or OpenAI's Decisions API instead. A decision model may make a gate stricter, never looser, and every decision is logged so the learning loop can score it.

07

A standalone core with a protocol

The core, exod, is a lean Python server with one typed, replayable event stream. The terminal, web, desktop, chat channels and a future device are all clients of it. A client that reconnects replays what it missed. A line budget keeps the core small enough to shrink onto a device.

08

Lifted with credit, improved on purpose

Exo is its own harness, not a fork. It lifts a small set of proven modules from Hermes Agent (MIT) and rewrites the rest small. Every lifted file carries a header and a row in a provenance file with its upstream path and commit. A weekly diff proposes ports, so upstream fixes still flow in, by choice rather than by dependency.

05 / The learning loop

It learns from you. Then it proves the lesson helps.

Most assistants that "learn" just save notes and hope. Exo fuses two ideas: a background reviewer that turns your feedback into lessons, and taste learning that shows what it learned right in the chat. Then it adds a test. A lesson is kept only if it scores better.

  1. 1

    Capture

    Corrections, edits, accepts, rejections, explicit asks and outcomes become ledger events. A correction is the strongest signal there is.

  2. 2

    Review

    A reviewer branches off the main thread and turns events into typed lesson proposals, each with evidence and confidence. It only proposes. It never edits in silence.

  3. 3

    Climb

    Each proposal becomes a candidate: the current setup with one change. It is scored on your own eval, built from your past decisions.

  4. 4

    Keep or drop

    Kept only if it scores better on held-out cases and passes regression gates. Otherwise it is dropped, or it becomes one clear question for you.

  5. 5

    Show

    Learned taste appears inline in the chat, linked to a plain file you can edit. Reverts are appended, never deleted, so every lesson can be traced.

n=1 evaluation

One person, measured over time. Public leaderboards are not the target. The question is: does Exo predict and please you better than it did last week?

What it is scored on

Questions about you with known answers. Pairs of what you rejected and what you chose. Replays of real past turns, cut just before your verdict. Split by time, with the newest held out.

How it is scored

Your hard rules become exact checks, and a break is a fail. A separate judge model scores the rest over many samples, checking stance and conclusions, not just voice.

06 / One surface

Feels like a terminal. Summons an app when it helps.

Exo ships one surface, not a CLI plus a separate app. The base is a calm prompt and transcript. Three prefixes and one palette are the whole learning curve: / commands, @ context, ! shell, ctrl+p for everything else.

Richer elements are panels the model opens when they are relevant: a diff viewer, a task board, an approval card, a taste card, a session tree, a chart. Each client renders what it can. The web and desktop show full panels, the terminal shows a compact form, and a device can show a card or speak.

You can always open or close a panel yourself. Those choices feed the learning loop too: an ignored panel teaches as much as an opened one.

07 / Principles

The rules every design call answers to.

Exo has eighteen principles, distilled from a long reading of the guardian-angel essay and the pages it links to. These nine carry the most weight.

  1. P01

    The log is the source of truth.

    Everything else is a view that can be rebuilt when a model or format changes.

  2. P02

    Amplify the person. Do not replace them.

    You decide what is worth doing. Agents decide how, inside your goals.

  3. P03

    Attention is the scarcest resource.

    The aim is not zero interruptions. It is zero wasted interruptions.

  4. P04

    Ask when unsure. Act when confident.

    And measure the uncertainty, instead of guessing at it.

  5. P05

    Every correction sticks.

    A correction changes future behaviour the same day. Say it three times and Exo proposes a rule.

  6. P10

    Content is data.

    Instructions come only from your channel, never from an email, a web page or tool output.

  7. P11

    Gate by reversibility and exposure.

    Not by step count. Fast where mistakes are cheap, careful where they are not.

  8. P12

    Evaluate on n=1, over time.

    Predict your next decision before you make it, and score the prediction.

  9. P17

    Models are swappable parts.

    The value is in your record, your store and the harness. The model is a part you can change.

08 / Status and roadmap

Early. In active build. Here is exactly where it stands.

Exo is not a product you can install today. It is being built in waves, each with a clear exit test. Right now the wave 1 core is being wired end to end and run through its acceptance checks. This page will change as the work does.

Built: wave 1, the core skeleton

  • Model router with fallback, for Anthropic and OpenAI-compatible APIs, including local models, plus a decision role
  • Tool registry with file, search, patch and shell tools, and hooks that can block a call
  • Turn loop that builds context from a summary tree, with sessions that fork and resume
  • Plugin loader and memory and context slots
  • Provenance tracking for every module lifted from upstream
  • The exod server with a replayable event stream, and a line client

Built earlier, being moved onto the new core

  • Signed, hash-chained ledger and the principal store
  • Importers for Claude Code, Hermes, and claude.ai, ChatGPT and Grok exports
  • Consolidation of corrections into reviewed belief proposals, and taste
  • Ask loop, n=1 eval and a daily brief
  • Action gates, a signed agent-to-agent bus, and an onboarding interview

  1. Wave 1 · Built

    Core skeleton

    Loop, providers, tools, sessions, slots, plugin loader, protocol server, provenance.

  2. Wave 2 · Next

    Re-home

    Memory, context, gates, command centre, bus and orchestra on the new core. Skills and MCP.

  3. Wave 3

    UI and learning

    Terminal and web clients, model-summoned panels, the learning loop with hill-climbing eval.

  4. Wave 4

    Channels and cutover

    Chat channel adapters, history import, and real seats moving over, each with a rollback.

  5. Wave 5

    Device

    Footprint audit, local small-model defaults, the core on a small board, a thin device client.
